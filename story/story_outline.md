## 1. 总体架构：每人三段挂在哪

`constants.ts` 的 `LEVEL_STORIES` 就是钩子，触发机制**已经实现**（详见下面「落地方式」）。

### 三段的位置与职能

| # | 触发 | 阈值 | 职能 | 一句话 |
|---|---|---|---|---|
| **① 靠近** | 親密度 Lv.3「朋友」 | 90 | 破人设 | 第一次**特意**两个人待在一起，你看见她不表演自己角色时的样子 |
| **② 裂缝** | 好感度 Lv.3「心动」 | 140 | 露内核 | 她的表层性格是用来盖住什么的——那个东西露出来了。**玩家选择在这一段权重最大** |
| **③ 回答** | 好感度 Lv.5「挚爱」 | 220 | 收束 + CG | 对①②埋的东西给出回答 |

⚠️ **上面这三格是"位置"，不是"模板"。**
每个角色的故事风格必须不一样——铃那条是安静的考据、真希那条是关西腔的嘴硬、
稻荷那条带千年神明的时间尺度。不要把三个人写成同一个结构换皮。
表格只是说明"大约在什么关系深度触发"，具体这个人的三段该怎么切、切几段、
哪一段该长哪一段该短，写到谁就按谁来定。

触发轴同样是**每个角色可配的**（见 `LEVEL_STORIES` 的 `axis` 字段）。
默认建议 ①走親密度、②③走好感度：这样「只想交朋友」的玩家也能拿到①，
不会被恋爱线整个挡住。要全挂好感度也只改数据、不动代码。

### 落地方式（已实现）

`constants.ts` 的 `LEVEL_STORIES` 现在是这个形状：

```ts
export const LEVEL_STORIES: Partial<Record<CharacterId, LevelStoryDef[]>> = {
  // [CharacterId.ASUKA]: [
  //   { id: 'asuka_1', axis: 'familiarity', level: 3, titleZh: '委員長の放課後', titleEn: '...' },
  //   ...
  // ]
};
```

- 关系升到某一级时，`App.handleLevelUpContinue` 先查 `findLevelStory(char, axis, level)`；
  **查到且 `script` 有内容 → 播手写剧本**（走 StoryScreen，和序章同一套引擎）；
  查不到 → 照旧让 AI 即兴演出。
- 所以**可以一个角色一个角色地写**：没写的角色行为完全不变，游戏不会卡。
- 手写剧本白拿：打字机、带属性门槛的选项、`requiresFlag`、生词进单词本、
  属性/关系增减、CG 解锁、`branch` / `random`、存档续玩、回想、自动/快进。

## 3. 怎么写（格式建议）

**把 `chapter1_script.md` 从散文改写成数据。** 现在它是 Markdown 散文，而序章是 `StoryNode[]`。改成数据格式，下面这些**全部白拿**，一行不用写：

逐字打字机 · 选项 + 属性门槛 · 生词自动进单词本 · 属性/关系增减 · CG 解锁 · 便利店式购物 · `branch` 条件插播 · `random` 随机加演 · 存档续玩 · 回想 backlog · 自动播放 / 快进 / 跳过

建议目录：

```
story/
  day1Data.ts              第一天正文（StoryNode[]）
  day1Meta.ts              版本号、flag 文案（仿 prologueMeta.ts）
  levelStories/
    hikari.ts  asuka.ts  rei.ts  inari.ts
    nao.ts     sora.ts   miyuki.ts  maki.ts
```

每段专属剧情建议 **25–40 个节点**（序章一条傍晚路线约 30 个），含 1 个关键选择。

`chapter1_script.md` 保留为**写作草稿**，`.ts` 是最终上线版——就像 `prologue_script.md` 和 `prologueData.ts` 现在的关系。

### 每场自检清单
- [ ] 有没有至少 1 个 `words`（这是日语学习游戏，生词是主收益）
- [ ] 属性增减的 `reason` 写清楚了没有（会显示在 StatGainToast 上）
- [ ] 关系变动挂在 `relations` 上，别忘了 `char`
- [ ] 立绘 `characterImage` 只在需要换人/退场时写；不写=保持不变
